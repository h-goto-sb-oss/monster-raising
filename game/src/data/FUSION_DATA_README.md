# fusionRecipes.json の読み方

`monster_project/build_fusion_recipes.py` が自動生成する。**手で編集しない**。
生成し直すには次を実行する。

```
python monster_project/build_fusion_recipes.py
```

入力は読み込み専用の 3 ファイル
(`step2_dedup/monster_master_330.json` の採用285体、`step3_fusion/type_fusion_matrix.json`、
`step3_fusion/fixed_recipe_seeds.json`)。

## なぜ自動生成なのか

手設計レシピは 30 件しかなく、実測すると最上位29体のうち野生から到達できるのは
**1 体だけ**、上位57体のうちレシピが存在するのは 11 体だけだった。これでは遊べないので、
手設計30件を最優先の特殊レシピとして温存したまま、全モンスターへ経路が通る基本表を機械生成している。

## 階級の決まり方

血統(bloodline)と相手(partner)の階級を比べる。

| 血統 | 相手が同格以上 (`up`) | 相手が格下 (`same`) |
| --- | --- | --- |
| ★1 下位 | ★2 中位 | (格下が無いので存在しない) |
| ★2 中位 | ★3 上位 | ★2 中位 |
| ★3 上位 | ★4 最上位 | ★3 上位 |
| ★4 最上位 | ★4 最上位 | ★4 最上位 |

`same`(横移動)は、中位・上位で袋小路にならないための逃げ道。
格下を食わせると **階級は上がらないがタイプや個体は変えられる**。
横移動で血統自身が返るだけの組み合わせは、2体消費して1体戻る罠になるので生成しない。

## 結果タイプの決まり方 (`type_rule`)

原則は DESIGN_NOTES.md の「血統側のタイプが子の基本タイプ」。
ただし目標階級にそのタイプが1体も存在しないことがある
(スライムは下位4体のみ。最上位はけもの/不死/幻魔/物質の4タイプにしか存在しない)。
そこで次の順に降り、**どの規則が発火したかを必ず記録する**。

| コード | type_rule | 内容 | 件数 |
| --- | --- | --- | --- |
| 0 | 血統タイプ | 原則どおり血統のタイプ | 3797 |
| 1 | 相手タイプ | 血統タイプが目標階級に居ないので相手側へ寄せる | 112 |
| 2 | 行列既定タイプ | `type_fusion_matrix.json` の `result_primary_type` | 0 |
| 3 | タイプ代替 | それでも駄目なら、その階級で最も層が厚いタイプへ | 99 |

コード2が0件なのは、行列の `result_primary_type` が全100行で `bloodline_type` と
等しく、規則1と同値だから。監査用に連鎖へは残してある。

## ファイル構造

```jsonc
{
  "meta":         { ... 生成日時・引き方・件数 ... },
  "tier_order":   ["下位","中位","上位","最上位"],
  "tier_advance": {"下位":"中位", ...},
  "wild_tiers":   ["下位","中位"],          // 野生で捕まえられる階級 = 初期所持
  "type_rules":   ["血統タイプ","相手タイプ","行列既定タイプ","タイプ代替"],
  "special": [                              // 手設計30件。原文どおり保持
    { "recipe_id":"F001", "source":"手設計", "recipe_kind":"固定×固定",
      "bloodline_id":"U2-03", "partner_ids":["U2-10"], "result_id":"U4-06",
      "result_tier":"上位", "result_type":"物質", "type_rule":"手設計",
      "hidden":true, "rationale":"..." }
  ],
  "by_bloodline": {                         // 自動生成4008件
    "U1-02": {
      "up":   { "result_tier":"中位", "hidden":false,
                "partners": { "けもの": ["U2-05","けもの",0] } },
      "same": null
    }
  }
}
```

### なぜ総当たりではないのか

285×285=81,225 通りを列挙するとファイルが巨大になる。だが結果は
**(血統の個体, 相手のタイプ, 階級の向き)** だけで決まる — 相手のどの個体かは影響しない —
ので、その3つで引ける表に畳んである。現在 4008 エントリ / 約168KB。
存在し得ない相手(例: 中位以上のスライムは0体)のキーは最初から作らない。

- `partners` の値は `[result_id, result_type, type_rulesへの添字]` のタプル。
- `result_tier` と `hidden` は向き単位で共通なので上位階層へ括り出してある。
- 自動生成分の `recipe_id` は保存せず、`G:<bloodline_id>:<direction>:<partner_type>`
  という決定的な書式で UI 側が組み立てる(再生成しても不変)。

## 引き方 (`src/engine/fusion.js` の `resolveFusion`)

1. `special` を `(bloodline_id, partner_ids === [partner_id])` の完全一致で探す。**手設計が最優先**。
2. 無ければ `direction = 相手の階級 >= 血統の階級 ? "up" : "same"` を求め、
   `by_bloodline[血統id][direction].partners[相手のタイプ]` を引く。
3. それも無ければレシピ無し。UI は「配合レシピがありません」と明示する。

いずれも O(1)。

## hidden について

`hidden: true` は ★3(上位) / ★4(最上位) の結果。GAME_SPEC_V0_1.md 3章に従い、
一度作るまで名前を伏せて「？？？」と表示する。発見済みidは localStorage の
`mrg_discovered` に貯まり、2回目以降は名前が出る。

## 到達可能性の保証

生成スクリプトは、**野生入手可能な下位+中位の199体だけ**を初期集合として
レシピを不動点まで適用するシミュレーションを内蔵している。
上位57体・最上位29体が 100% 到達可能でなければ、孤立individualを列挙して異常終了する。

現状の結果:

```
下位  : 136/136 到達 (100.0%)
中位  :  63/ 63 到達 (100.0%)
上位  :  57/ 57 到達 (100.0%)
最上位 :  29/ 29 到達 (100.0%)
```

## 既知の制限

- `special` のうち7件は相手が2体の「複数固定の特殊合体」。現UIは相手1体しか
  選べないため、この7件は成立しない(データには保持済み)。
- 所持は v0.1 では「種族単位のユニークid」で、同じ種族を2体持てない。
  そのため「同じモンスター同士の配合」も現状は選べない。
- 能力値・技の継承は未実装。配合結果は結果モンスターの既定ステータスをそのまま使う。
